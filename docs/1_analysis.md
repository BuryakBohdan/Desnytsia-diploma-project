# РОЗДІЛ 1. АНАЛІТИЧНА ЧАСТИНА

## 1.2. Аналіз існуючих аналогів

У межах кваліфікаційного проєкту виконано глибокий інженерний скаутинг та порівняльний аналіз трьох існуючих програмних систем-аналогів, які вирішують завдання віддаленого управління та підтримки: TeamViewer, AnyDesk та RustDesk.

### Технічний опис аналогів

#### 1. TeamViewer
* **Архітектурний патерн:** Розподілена гібридна архітектура з використанням централізованих маршрутизуючих релей-серверів та P2P-з'єднання. Залежність від інфраструктури провайдера призводить до додаткових затримок (Latency) при перенаправленні трафіку через проміжні вузли.
* **Протоколи передачі даних:** Закриті пропрієтарні протоколи поверх TCP/UDP із шифруванням сесій за допомогою RSA (4096-bit) та AES (256-bit).
* **Стек даних:** Централізовані реляційні БД для управління обліковими записами та In-Memory кешування на релей-вузлах.
* **Технічні обмеження (Technical Bottlenecks):** Закритий вихідний код, висока вартість ліцензування, залежність від закритих серверів аутентифікації та потенційні вузькі місця при пікових навантаженнях.

#### 2. AnyDesk
* **Архітектурний патерн:** Децентралізована архітектура з акцентом на прямі P2P-з'єднання та використання спеціалізованого кодеку DeskRT, що знижує мережеві затримки.
* **Протоколи передачі даних:** Оптимізований протокол на базі UDP для передачі відеопотоку, шифрування TLS 1.2 та RSA 2048.
* **Стек даних:** Розподілені сервери каталогів для швидкого пошуку хостів та ведення сесій.
* **Технічні обмеження (Technical Bottlenecks):** Пропрієтарна кодова база, складнощі з глибокою кастомізацією під вбудовані системи Android без прав суперкористувача (Root).

#### 3. RustDesk
* **Архітектурний патерн:** Відкрита (Open-source) клієнт-серверна архітектура з підтримкою розгортання власних серверів сигналізації та релеїв (Self-hosted).
* **Протоколи передачі даних:** WebRTC (ICE, STUN/TURN), WebSockets, шифрування на базі NaCl cryptobox.
* **Стек даних:** SQLite або PostgreSQL для серверів сигналізації.
* **Технічні обмеження (Technical Bottlenecks):** Необхідність самостійного адміністрування інфраструктури релей-серверів, потенційні складнощі стабілізації з'єднання в умовах агресивних корпоративних мережевих екранів (Firewalls).

### Порівняльна інженерна матриця

| Критерій порівняння | Наш проєкт («Десниця») | TeamViewer | AnyDesk | RustDesk |
| :--- | :--- | :--- | :--- | :--- |
| **Тип архітектури** | Розподілена мікросервісна / Event-Driven з P2P-модулем | Гібридна (централізовані релей-сервери + P2P) | Децентралізована P2P з оптимізованим кодеком | Клієнт-серверна з можливістю self-hosted розгортання |
| **Протоколи обміну (API)** | WebRTC, WebSockets, gRPC, зашифровані SMS-тригери | Закритий власний протокол поверх TCP/UDP | Власний UDP-протокол (DeskRT) | WebRTC, WebSockets, TCP |
| **СУБД та консистентність** | PostgreSQL + Redis (In-Memory кеш сесій) | Закрита пропрієтарна БД / In-Memory релеї | Реляційні розподілені сервери каталогів | SQLite / PostgreSQL (Self-hosted) |
| **Швидкодія (Latency / RPS)** | Низька латентність завдяки прямому P2P WebRTC-потоку | Середня/Висока залежно від завантаження релей-вузлів | Висока завдяки власному кодеку DeskRT | Висока за умови оптимізованого TURN-сервера |
| **Відмовостійкість (Fault Tolerance)** | Висока (P2P + аварійний канал через зашифровані SMS-тригери) | Середня (залежність від інфраструктури вендора) | Середня (залежність від серверів каталогу) | Висока (контроль інфраструктури через self-hosted) |
| **Безпека (Security)** | End-to-End шифрування, інтеграція з Android Accessibility API | RSA-4096 / AES-256 (закритий код) | TLS 1.2 / RSA-2048 | NaCl cryptobox (Open-source аудит) |

### Аналітичний висновок

Проведений інженерний аналіз існуючих аналогів (TeamViewer, AnyDesk, RustDesk) засвідчив, що більшість комерційних рішень базуються на пропрієтарних, закритих протоколах та централізованих релей-серверах. Такий підхід створює критичні архітектурні обмеження, зокрема залежність від інфраструктури сторонніх вендорів, високі мережеві затримки (Latency) при проходженні трафіку через проміжні вузли, а також неможливість глибокої програмної інтеграції зі спеціалізованими системними службами мобільних ОС Android без компрометації безпеки.

З метою усунення виявлених індустріальних недоліків, у межах кваліфікаційного проєкту «Десниця» обрано відкритий і масштабовний стек, що базується на комбінації протоколів WebRTC та WebSockets для реалізації прямого низьколатентного P2P-обміну даними. На відміну від монолітних або жорстко централізованих схем конкурентів, запропонована архітектура поєднує сучасні методи управління станом за допомогою стійких мікросервісних компонентів, а також реалізує унікальний інженерний механізм аварійного відновлення з'єднання через зашифровані SMS-тригери. Це забезпечує високий рівень відмовостійкості (Fault Tolerance) і автономності керування в умовах нестабільного інтернет-трафіку або повної відсутності мережевого з'єднання, що повністю відповідає сучасним вимогам інженерії програмного забезпечення.
