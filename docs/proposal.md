# Thesis Proposal: Розробка розподіленої системи «Десниця» для віддаленого адміністрування та технічної підтримки Android-пристроїв

*Development of the "Desnytsia" Distributed System for Remote Administration and Technical Support of Android Devices*

## 1. Актуальність та проблематика

Значна частина користувачів ОС Android має низький рівень цифрової грамотності (зокрема користувачі старшого віку) та потребує віддаленої допомоги під час конфігурації пристрою або усунення програмних збоїв. Наявні рішення для віддаленого доступу загального призначення (TeamViewer, AnyDesk) потребують від користувача кількох ручних дій: встановлення, передавання коду сесії, надання дозволів.

Основні технічні проблеми:

- забезпечення низьколатентного захищеного з'єднання за нестабільного інтернет-каналу або NAT/firewall на стороні клієнта;
- відновлення керування пристроєм після повної втрати інтернет-з'єднання;
- захист каналу керування від перехоплення, підміни команд та повторного відтворення (replay);
- мінімізація кількості ручних дій з боку користувача пристрою за умови збереження його явної згоди на сесію керування.

Мета проєкту: розроблення розподіленої системи «Десниця», що забезпечує віддалене адміністрування Android-пристроїв із резервним каналом відновлення зв'язку через SMS та контуром спостережуваності й автоматизованого контролю якості.

## 2. Ідея продукту та архітектурний тип

Продукт є розподіленою клієнт-серверною системою з P2P-взаємодією, що складається з таких компонентів:

- **Android-застосунок «Десниця»** (клієнтська частина на пристрої користувача та на пристрої адміністратора);
- **Signaling Server** — сервер сигналізації та керування сесіями;
- **STUN/TURN-сервер** — для встановлення P2P-з'єднань за NAT та ретрансляції трафіку у разі їх неможливості;
- **Сховище даних** — реляційна БД для журналу аудиту та кеш-сховище для стану сесій;
- **Контур спостережуваності** — збір та візуалізація метрик.

Архітектура побудована за принципом подієво-керованої взаємодії (Event-Driven Architecture). Мультимедійні дані та керуючі команди передаються напряму між вузлами за протоколом WebRTC. Сервер виконує лише функції сигналізації, автентифікації та аудиту. Відмовостійкість забезпечується автоматичним перепідключенням (ICE restart, reconnect з експоненційною затримкою), ретрансляцією через TURN та резервним каналом керування через SMS.

## 3. Детальний опис функціоналу (Core Features)

1. **Трансляція екрана в реальному часі.** Захоплення кадрів інтерфейсу за допомогою `MediaProjection API` (у складі foreground-сервісу) та передавання відеопотоку з мінімальною затримкою через WebRTC Video Track.
2. **Віддалене керування інтерфейсом.** Програмна імітація жестів (натискання, свайпи, введення тексту) за допомогою `AccessibilityService`.
3. **Сигналізація та керування сесіями.** Signaling Server (Ktor, WebSockets) для обміну SDP/ICE-повідомленнями, маршрутизації P2P-з'єднань та керування життєвим циклом сесій. Стан сесій зберігається в Redis.
4. **Канал обміну даними (Data Channel).** Передавання керуючих команд, системних логів та статусів з'єднання через WebRTC Data Channel.
5. **Резервне відновлення зв'язку через SMS.** Моніторинг стану мережі (`ConnectivityManager`) та обробка вхідних SMS через `BroadcastReceiver`. Команди відновлення з'єднання підписуються HMAC-SHA256 та містять часову мітку й одноразовий nonce для захисту від replay-атак.
6. **Автентифікація та безпека.** Автентифікація адміністратора за JWT (access/refresh токени), TLS для каналу сигналізації, DTLS-SRTP для медіапотоку WebRTC. Початок кожної сесії потребує явної згоди власника пристрою, активна сесія має видимий індикатор.
7. **Журнал аудиту та спостережуваність.** Фіксація подій сесій (початок, завершення, виконані команди, помилки) у PostgreSQL. Експорт метрик сервера (кількість сесій, затримка сигналізації, частота перепідключень) для Prometheus та візуалізація в Grafana.

## 4. Попередній технологічний стек

| Категорія | Технології |
|---|---|
| **Мови програмування** | Kotlin (клієнтська та серверна частини) |
| **Фреймворки та бібліотеки** | Android SDK, Jetpack Compose, Ktor (сервер), WebRTC Android SDK, Kotlin Coroutines/Flow |
| **Архітектурні патерни** | Clean Architecture, MVVM, Event-Driven Architecture, Repository |
| **Мережеві протоколи** | WebRTC (Video Track, Data Channel), WebSockets, STUN/TURN (coturn), TLS, DTLS-SRTP |
| **Системні API Android** | MediaProjection API, AccessibilityService, BroadcastReceiver, ConnectivityManager |
| **Бази даних** | PostgreSQL (журнал аудиту), Redis (стан сесій) |
| **Безпека** | JWT, HMAC-SHA256, TLS, перевірка залежностей (OWASP Dependency-Check) |
| **Тестування та якість** | JUnit 5, MockK, Espresso, k6 (навантажувальне тестування сервера), SonarQube |
| **DevOps та спостережуваність** | Git, Gradle, Docker, Docker Compose, GitHub Actions (CI/CD), Trivy, Prometheus, Grafana |
| **Розгортання** | Хмарна VPS-інфраструктура (серверні компоненти в контейнерах) |

### Обґрунтування вибору стеку

- **Kotlin для клієнта й сервера** — єдина мова зменшує вартість підтримки та дозволяє перевикористовувати моделі даних і протокол обміну повідомленнями.
- **WebRTC** — стандартизований протокол із вбудованим шифруванням (DTLS-SRTP) та механізмами проходження NAT, що підходить для низьколатентної передачі відео та команд.
- **Ktor** — легкий асинхронний фреймворк на корутинах з нативною підтримкою WebSockets.
- **PostgreSQL та Redis** — транзакційне зберігання журналу аудиту та швидкий доступ до короткоживучого стану сесій.
- **Docker, GitHub Actions, Trivy, SonarQube, k6** — відтворюване розгортання та автоматизований контроль якості і безпеки на кожному етапі CI/CD.

## 5. Обмеження та припущення

- Розповсюдження застосунку передбачається поза Google Play (APK), оскільки політика магазину обмежує використання `RECEIVE_SMS` та `AccessibilityService` для віддаленого керування.
- Для `MediaProjection` на нових версіях Android потрібна згода користувача на кожну сесію захоплення екрана.
- Система призначена для використання лише за явної згоди власника пристрою.
